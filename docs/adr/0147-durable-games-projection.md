# ADR-0147 — Durable, event-log-driven games projection

**Status:** Proposed for owner review
**Date:** 2026-09-26

## Context

`docs/DATABASE.md` §4.2 defines `games` as a projection of `game_events` that can be rebuilt, but nothing derived it. Verified on `main` at `93cc29c`:

- Seek acceptance (`PgSeekAcceptor`) and bot games (`PgGameStarter`) insert a creation-time row in the same transaction as `GameCreated`. Tournament games (`DurableGameLauncher`) and any other `EventStore.append(…, -1, …)` caller, such as `GameAuthority.createGame`, write events only and get no row.
- `GamesRepository.updateProgress` and `finish` had no runtime callers. Rows kept a ply count of 0, `last_seq = 0` and a NULL `result`, `termination` and `ended_at` forever. `GET /v1/games/:id`, `/v1/users/:handle/games`, the ended-game seek receipt guard (`games.ended_at`), search indexing and achievements therefore read stale or missing state.
- `server_ts` is `now()` at statement time and `seq` is per game, so neither orders commits globally. A cursor over either can pass a row whose transaction commits later.

## Decision

1. **One writer.** `PgGamesProjector` (`packages/persistence/src/pg/games-projector.ts`) is the only code that updates `games` after creation. The unused non-monotonic `start`, `updateProgress` and `finish` are removed from `GamesRepository` and `PgGamesRepository`. The two creation transactions keep inserting their row, so a new game is readable at once, and the projector reconciles those rows. The creation, append and player-lock paths are unchanged. No shadow table is added.
2. **Work position from transaction ids.** Migration 0040 adds `game_events.xact_id xid8 NOT NULL DEFAULT pg_current_xact_id()`, which is the id of the transaction that wrote the row, and migration 0041 builds the `(xact_id, game_id, seq)` index online (`CREATE INDEX CONCURRENTLY`), outside the column rewrite's exclusive lock. A batch reads rows after the `projection_checkpoints` position whose `xact_id` is below `pg_snapshot_xmin(pg_current_snapshot())`. Every transaction below that horizon has finished. A transaction still running has an id at or above it, so its rows sort after anything the checkpoint can pass and a later batch reads them. The default fills the column for every existing writer, so no append code changes.
3. **Atomic batches, one replica at a time.** A batch is one transaction. It locks the checkpoint row `FOR UPDATE SKIP LOCKED`, so a concurrent projector returns `busy` without reading anything. It projects the games touched by up to 500 events plus up to 20 due retries, and it advances the checkpoint to the last event read. All of these commit together. A crash or shutdown before `COMMIT` leaves the rows, failure records and checkpoint exactly as they were.
4. **Re-fold, then guard.** Each touched game is re-folded from its complete committed stream by the pure `projectGameStream` (`packages/persistence/src/games-projection.ts`). The fold uses the canonical `classifySpeed`, takes `started_at` and `ended_at` from the event timestamps, the ply count from the last `MovePlayed.ply` and `last_seq` from the stream head. The upsert applies only `WHERE games.last_seq <= EXCLUDED.last_seq`. Replays, a rebuild overlapping a live batch and stale work are therefore no-ops and never regress a row. A seat that is not a registered account projects as NULL, as the nullable user foreign keys allow, rather than failing the stream. `opening_eco` is not in the log and is not projected.
5. **Corrupt streams are durable work, not skipped work.** Each game is projected inside a savepoint. An upcast error, an impossible stream (not starting with `GameCreated`, a seq gap, a second creation, an out-of-order ply, anything after `GameEnded`) or a constraint violation rolls back only that game. The failure is written to `games_projection_failures` in the same transaction that moves the checkpoint past its events, and it is logged. The failure is retried after 2^attempts seconds, capped at one hour, and immediately whenever the stream gets a new event. A successful re-fold deletes the record. Only failures caused by the stream's own data are recorded this way (projection errors, and SQLSTATE classes 22 and 23). A lost connection, timeout, cancellation or conflict instead aborts the whole batch, so the checkpoint does not move past a healthy game and the worker backs off.
6. **Runtime.** Every gateway with `DATABASE_URL` runs a `GamesProjectionWorker`. That is already true in Compose and in the Helm gateway and search-indexer Deployments, so no deployment change is needed. The worker runs batches back to back while a page is full, polls every second when caught up, and backs off exponentially up to 30 s after a failed batch. On shutdown it stops scheduling first, and the in-flight batch is awaited before pub/sub and the pool close.
7. **Consumers wake after the row commits.** When a committed batch makes a row terminal, the gateway publishes an `ended` broadcast on `gamesProjectedEndedChannel()`. A row lock makes that transition belong to exactly one committed batch. The search indexer and the achievements worker now subscribe there instead of to `gamesEndedChannel()`, which fires before the projection can have caught up. The gateway starts its projector only after those workers subscribe, and on shutdown it unsubscribes them only after the in-flight batch has published. Terminal-event consumers that read the event log (the tournament reporter and the bot and anti-cheat analyzers) are unchanged.
8. **Backfill.** Rows written before 0040 all carry the migration's transaction id. The first batch after deploy therefore replays the whole log without an operator step. `npm run games:rebuild` (in `@chess-platform/persistence`) re-folds every stream independently of the checkpoint. It is repeatable and safe beside live projectors and appends because of the guard in point 4. Each rebuild page runs under REPEATABLE READ and leaves to the live projector any game with a committed event past the checkpoint that this cluster wrote. The deferral decision and the folds it guards read one snapshot, so a game that ends during a rebuild is still reported by the live batch that publishes wakes instead of being made terminal silently by the rebuild. A page that collides with a live write is retried. When the checkpoint carries another cluster's transaction ids, as after a logical restore, nothing is deferred: the rebuild repairs every game itself, even with no gateway running.

## Alternatives rejected

- **A `server_ts` or insertion-order cursor.** It can permanently skip a row whose transaction commits after a later-started one, which is the defect this ADR exists to close.
- **Projecting inside the append transaction or through a trigger** (the literal reading of `docs/DATABASE.md` §6). A projection defect, such as a foreign key, a missing upcaster or a malformed payload, would then reject the authoritative append. It would also lengthen transactions that hold the `rocky:active-human-game:` advisory locks, and a trigger would duplicate `classifySpeed` in SQL.
- **A dirty-games queue written by every append.** Every move would take a row lock that the projector also holds, which adds contention on the hot path and on player-locked creation.
- **Per-stream discovery by diffing `game_events` heads against `games.last_seq`.** It is correct, but every poll scans all games.

## Limits and follow-ups

- The horizon is cluster-wide. A long-running or idle-in-transaction session in any database on the server delays projection until it ends. This is lag, never loss. Operators should set `idle_in_transaction_session_timeout`.
- A logical restore into a different cluster can leave the checkpoint above that cluster's transaction counter. The projector detects this (checkpoint ≥ horizon), logs a warning and replays from the origin. Restored rows whose ids exceed the new counter are only reached as it catches up, so run `npm run games:rebuild` after such a restore. Physical replicas and `pg_upgrade` keep the counter.
- Migration 0040 rewrites `game_events` once under an exclusive lock to fill the column, which blocks appends for the duration. Before launch that is acceptable. At scale the column would be added nullable and backfilled. The index is already built online by 0041.
- Each touched game is re-folded in full, so a batch costs O(stream length) per game. That is bounded by game length and suits current volumes. An incremental fold from `last_seq` is the upgrade path if that changes.
- The post-projection wake is pub/sub: at most once and lossy, like today's channel. Search and achievement recovery from missed wakes is still not durable. Achievements additionally need an atomic per-game award key before any replay, and every replica with `ACHIEVEMENTS_ENABLED=1` still awards on each wake, as it did before. `games:rebuild` publishes nothing: endings it makes terminal (games the live projector had already passed, such as repairs or data from another cluster) wake no consumer; rerun `reindex-search` if those matter.
- Out of scope: ratings and rating pools, leaderboards, readiness, first-move clock start, no-show and seek lifecycle, and autonomous flag expiry. Ratings will consume this projection in a later increment.

# ADR-0149 — Autonomous server-authoritative in-play flag expiry

**Status:** Proposed for owner review
**Date:** 2026-09-27

## Context

Verified on `main` at `5036d68` (after PR #72, ADR-0148):

- A timed game ended on time only when something reached its owner: a late move (`Game.playMove` charges the clock first and records the timeout instead) or a player's `claimFlag`. Nothing on the server watched a running clock. With both players disconnected, the log said "ongoing" forever while every client clock showed zero. The audit's P0 "Timed-match lifecycle" lists it (`FABLE_ASTRA_FULL_AUDIT.md` §5, §14 #6: "server ends flagged games without a claim (incl. both-disconnected)").
- The clock is a pure fold. `hasFlagged(clock, side, now, tc)` holds when `remaining − max(0, now − turnStartedAt − delay) ≤ 0`, the delay applying only to `kind: 'delay'`. Each `MovePlayed` stores the charged `moveTimeMs` and the resulting `remaining`. Replay recomputes `remaining` from `moveTimeMs` with the same arithmetic, so for any stream the domain wrote the stored value equals the replayed one, and the next turn starts at the move's `at`.
- ADR-0148 left two clock lifecycles. A seek or tournament game has no anchor until its first move. A bot or direct game keeps the creation anchor, so White's clock runs from `GameCreated.at`.
- A player command reaching the owner after the side to move had flagged was applied as usual. A resignation or draw acceptance there beat the timeout if it arrived before anyone claimed, so the outcome depended on arrival order.
- PR #72's `NoShowExpiryWorker` is the proven pattern: a trigger-kept queue, a worker on every replica that re-decides from the log, and routing to the owner as a reserved actor, with the owner's command lock and the log's `expectedSeq` as the only correctness mechanisms.

## Decision

1. **Scope: a clock the first move started.** Autonomous expiry applies to every timed game (sudden death, increment, delay, every variant) once its first accepted move has been played. That is the point the ADR-0148 policy names, and the point from which every source has the same running clock. Unlimited games never expire. Seek, tournament, bot and direct games are all included after their first move: a flag is a chess rule, not a source policy, and a first-party engine plays through the same owner and command path as a human. Before the first move nothing changes. Sourced games have no running clock and are governed by the no-show rule. Bot and direct games keep their original lifecycle (a move or claim after the creation-anchored flag still records the timeout, as before). This increment adds no pregame policy for them.
2. **One canonical deadline.** `flagDeadline(clock, side, tc)` in `packages/game/src/clock.ts` returns the first instant `hasFlagged` holds: `turnStartedAt + delay + remaining`, or `turnStartedAt` when nothing remains, or `null` for unlimited or unanchored clocks. `Game.flagDeadline` exposes it only for an ongoing game with a move. `Game.timeoutDue(at)` is `hasFlagged` under the same scope. Every decision uses `hasFlagged`. The deadline only indexes the queue, and a unit test fixes the equivalence (`hasFlagged(d − 1)` false and `hasFlagged(d)` true for random clocks of every kind).
3. **The deadline decides, not the arrival order.** Once `timeoutDue(at)` holds on the owner, any player command it applies (a move, resignation, draw offer or acceptance, abort, readiness) records the timeout instead, with the same event `claimFlag` records. The late move was already handled this way. This extends it, as ADR-0148 did for the no-show. With deadline `T` and the owner's clock `t` when it applies a command: at `t < T` a legal move is played and replaces the deadline; at `t ≥ T` the timeout is recorded, whatever the command and whoever sent it. Insufficient mating material makes it a draw exactly as in `claimFlag`/`endByTimeout`, per variant.
4. **Server-only expiry command.** `expireFlag` is issued only as the reserved actor `FLAG_ACTOR` (`system:flag`). No client identity can take that form, and the wire decoder never produces the command. The owner refuses it unless `timeoutDue` holds on its own clock and its current copy, then appends `claimFlag`'s ending. The command carries no deadline or time.
5. **Durable queue.** Migration 0043 creates `flag_deadlines (game_id PK, seq, due_ms BIGINT)` with `flag_deadlines_due_idx (due_ms, game_id)` for the worker's keyset query. A `game_events` insert trigger keeps it in the append's own transaction, whichever code or release wrote it. A `MovePlayed` upserts the new side to move's deadline, and a `GameEnded` deletes the row. `flag_deadline_ms(game, move)` computes the deadline from the stored move and the game's `timeControl` with the same float8 operations in the same order as the JavaScript, then `ceil`, which is the first whole millisecond `hasFlagged` holds. `due_ms` is an exact integer because a `timestamptz` conversion rounds through microseconds and can read back a millisecond early. A value the domain would not write never raises. An unusable `remaining` or delay falls back to the move's `at`, a lower bound the worker corrects. An unusable `at` or a result outside the ECMAScript `Date` range gets no row. The migration backfills every game that is running when it commits from that game's latest move. `CREATE TRIGGER` holds a lock that blocks appends until the transaction commits, so no move can fall between the backfill and the trigger.
6. **Worker.** `FlagExpiryWorker` (`services/gateway/src/flag-expiry.ts`) runs on every gateway with `DATABASE_URL`, polling every `FLAG_SCAN_MS` (default 1 000). Each pass reads at most 50 due rows after a rotating keyset cursor and re-decides each game from the event log with the domain. If `timeoutDue(now)` holds, it routes `expireFlag` to the owner. If the log shows no clock that can flag, it dismisses the row. Otherwise it reschedules the row to the domain's deadline. Both corrections are guarded by `seq ≤` the log head it read, so neither can touch a row a newer move wrote. The queue is an index and the log is the authority. The pass loop, backoff, stop and routed expiry are PR #72's own code, moved into `deadline-expiry.ts` and shared by both workers. The pregame and in-play rules keep separate tables, commands, actors and decisions.
7. **Concurrency.** One owner applies a game's commands under its per-game lock, reading its clock inside the lock. A move applied first at `t < T` replaces the clock, so the expiry behind it is refused. At `t ≥ T` both a move and the expiry record the same timeout, and the second finds the game over. Across replicas both are routed to the single owner. A stale owner (split brain, lost lease) appends from a copy that missed the newer move, fails the log's `expectedSeq` check, reloads and decides again. A takeover reloads from the log before applying (ADR-0010). Two workers expiring one game both reach its owner, and the second is refused. Nothing can follow `GameEnded`.
8. **Ownership hygiene.** The PR #72 rule is unchanged and now shared. When nobody on the replica is watching, a lease claimed only for the expiry is released once the ending is visible, and a copy loaded only for it is evicted. A lease the replica already held, and a game with a local room, are left alone.
9. **Terminal integration.** The ending is an ordinary `GameEnded { termination: 'timeout' | 'insufficient_material' }` appended by the owner, so the committed-terminal-event reconciler (ADR-0144), the tournament reporter (a decisive or drawn result, never a relaunch), the games projection (ADR-0147: `result`, `termination`, `ended_at`), history, search, achievements and the seek-receipt live-game guard all consume it with no new path.

## Alternatives rejected

- **A timer per game (process, Redis key or browser).** It does not survive a restart and needs its own claim protocol. The log already has one.
- **Scanning running games each poll.** The cost grows with every live game. The trigger-kept queue holds exactly the running timed games, and the worker reads only due rows through an index.
- **Deriving due games from the games projection.** It lags the log, and a replica of another release could skip the fields.
- **The worker appending the ending directly.** The owner's cached copy would go stale (ADR-0148's reason).
- **Carrying the deadline on `MovePlayed`.** It would store a derived value that replay would then have to trust or re-check, and old events lack it. The trigger derives it from what replay already agrees with.
- **Stamping the ending at the flag instant.** `claimFlag` and the late-move path stamp the time the owner records the ending. Keeping one rule means a claimed timeout and an autonomous one are indistinguishable in the log, and the flag instant stays derivable from the log (`flagDeadline`).
- **Folding flags into `pregame_deadlines`.** The two queues differ in membership, in lifecycle (one row per game for its whole running life versus one entry until the first move), in timestamp exactness and in decision. A single table would blur which invariant each row serves.

## Limits and follow-ups

- An untouched flagged game ends within about one `FLAG_SCAN_MS` after its deadline. A touched one ends on the touching command. The ending's `at` is when the owner recorded it, so after downtime it is later than the flag instant, while the result is the same.
- The deadline is compared with the owner's clock. A worker whose clock runs ahead is refused and retries on the next pass, and the refusal is logged.
- The queue reads the `remaining` stored on each `MovePlayed`, which equals replay for every stream the domain wrote. A hand-edited stream could make a row early, which the worker corrects, or late.
- Migration 0043's backfill reads `game_events` once while the trigger's lock holds appends. Run it in a quiet window on large logs. Running games whose deadline passed while nothing watched them end on the first pass after deploy, which is what their logs already state.
- During a rolling deploy, a replica of the previous release owning a game refuses `expireFlag` (the reserved actor is not a seat there, and the worker retries), and does not apply the late-command rule to non-move commands. Replace every gateway replica in one rollout, as for ADR-0148.
- Bot and direct games before their first move keep the original lifecycle and are not expired autonomously. That needs a pregame policy of its own.
- Ratings, rating pools, leaderboards and the no-show policy are unchanged.
